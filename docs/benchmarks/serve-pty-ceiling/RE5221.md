# serve at the PTY ceiling (#60)

Measured 26 October 2026 on an Apple M5 Max (6 Super + 12 Performance cores), macOS 27.2, Node 24.14.1, headed Chrome 155 at DPR 2, 160×50. **Provisional:** the machine was shared with other agents' builds and benchmarks, and one-minute load averages ran from 7 to 16 during these runs (each run's load is in the JSON). Treat the numbers as an A/B under the same noise. They are not a clean comparison with Ghostty.

Builds: `pr57` is `a7849e2` (the #57 reader thread). `ring` is `1f48fa6` on this branch. Both are `packages/wraith/bin/wraithterm.mjs`, run alternately in the same session.

## What changed

1. **No stack traces for EAGAIN.** The #57 reader thread polls the non-blocking master, and every empty poll throws EAGAIN, about 1.5–3 times per 1 KiB read. V8 captured a stack trace for each one, and that capped the thread near 190 MB/s. This is where the "~185 MB/s PTY ceiling" came from: Python's blocking reader in `pty-ceiling.py` stalls at the same level for a different reason, which is a kernel wakeup on every 1 KiB. Setting `Error.stackTraceLimit = 0` in the thread lets a polling reader drain the PTY at 250–320 MB/s.
2. **A zero-copy shared ring.** The thread reads straight into a 4 MiB `SharedArrayBuffer`. It rings the main thread once per burst. The main thread sends ring views with cork/writev every 2 ms, and releases the bytes only after the socket has taken them. This removes one allocation and copy per batch in the thread, and three copies on the main thread (`Buffer.from` and two `Buffer.concat`). It also removes the pause/resume protocol: a backed-up socket leaves bytes in the ring, and a full ring stops the thread and with it the PTY.
3. **Clean disconnects.** When the socket closes, queued bytes are released, so the thread reads on to EOF and exits. With #57, a paused reader whose client disappeared stayed parked for the life of the process: the thread count stayed at 10 instead of returning to 8.
4. `TCP_NODELAY` on the socket.

## Why the browser path stays below serve's capacity

The engine is not the limit. A stub page that only answers the cursor-position query, with no Wraith at all, measured 110–234 MB/s, about the same as the real page. Serve's socket queue stayed empty, and the ring never filled. What changes is the PTY handoff itself. In instrumented runs with Chrome as the client, the reader saw 15,000–17,000 short gaps (10–50 µs) between 1 KiB reads, against 2,000–4,300 with a Node client. Its EAGAIN count rose from about 330k to 415k for the same bytes. The writer (`probe.py`) and the reader hand off every 1 KiB, and each handoff slows down when the system is busy with wakeups. Two synthetic thread pairs that only wake each other cut serve-alone capacity to 140 MB/s, and four pairs cut it to 90. A browser receiving 150+ MB/s generates exactly that kind of load: network-service reads, IPC to the renderer and worker messages. Ghostty pays the same PTY handoff, plus its parse on the reader thread.

## Tried and dropped

- **Blocking reads.** On a dedicated thread, blocking reads like Python's ran slower than polling: a 121 MB/s median against 153 in a reader microbenchmark.
- **Blocking only while idle.** Switching the master to blocking mode while idle, via the TTY handle's `setBlocking`, gave fast streaming and 0% idle CPU. But Node joins a worker blocked in `read()`, so `process.exit` hung for as long as a HUP-ignoring child kept the slave open. That was reproduced, and the idea was dropped.
- **Spin window.** A 1 ms or 5 ms spin before sleeping showed no consistent change in the browser A/B, so 0.2 ms stays.
- **Drain interval.** A 1 ms or 5 ms interval instead of 2 ms showed no consistent change.
