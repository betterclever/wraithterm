# Worker-owned socket against the page-owned socket in `serve`

Measured on 26 October 2026 on an Apple M5 Max (18 logical CPUs) running macOS 27.2, with headed Chrome 155 at DPR 2 and a 160×50 grid. The build was `0873abe` and the base was `perf/serve-coalesce`. The machine was shared with other agents running builds and benchmarks. One-minute load averages were 9.5–18.5 during the runs; each run's load is in [ab.json](ab.json). **All numbers here are provisional.** They compare two variants of one build, run interleaved on the same machine. They say nothing about native Ghostty.

## What is compared

Both variants run the same build of `wraithterm serve`. Only the page script differs:

- **worker:** the default page calls `term.connect('/pty?token=…')`. The engine worker opens the WebSocket (via `WebSocketStream`), parses each message, and sends keystrokes and replies itself.
- **page:** `?transport=page` opens the WebSocket on the main thread and calls `term.connect(socket)`. Every message is received on the main thread, then posted to the worker, which sends a `written` acknowledgement back.

[serve-ab.mjs](../../../scripts/ghostty-native/serve-ab.mjs) ran 6 rounds, alternating which variant went first. Each session runs [probe.py](../../../scripts/ghostty-native/probe.py) through a real PTY. The probe writes each workload, then waits for a cursor-position reply. It now records wall-clock start and end times for each workload. Over each of those windows, the script collects:

- **Main-thread task time:** Chrome's `Performance.TaskDuration`, sampled over CDP every 25 ms and interpolated to the window.
- **Frames:** `requestAnimationFrame` callbacks on the page, counted as frames per second and the longest gap between them.
- **Long tasks:** `PerformanceObserver` entries of type `longtask`.

Each session then measures keystroke echo through `cat`: 30 pastes 400 ms apart, timed from paste to the echo appearing in a rendered frame (the same method as `echo.mjs`). The workloads are the four used in the Ghostty comparison, regenerated locally. Logs and ASCII are 64 MB each. DOOM text is the first 30 MB of the 160×50 recording. DOOM Kitty is 59.5 MB, cut at a frame boundary.

## Results

Each cell shows the median of 6 runs, with min–max in brackets.

| Logs       | worker  | 66 (50–92) |          60 (38–69) |         6% (5–8) |     120 |          0 |
|            | page    |  67 (6–82) |      167 (144–1240) |      18% (11–19) |     120 |          0 |
| ASCII      | worker  | 62 (29–81) |         63 (40–106) |         5% (5–7) |     120 |          0 |
|            | page    | 60 (36–79) |       202 (150–274) |      18% (15–20) |     120 |          0 |
| DOOM text  | worker  | 59 (37–79) |          31 (21–50) |         6% (5–7) |     120 |          0 |
|            | page    | 61 (41–77) |         87 (72–127) |      18% (17–19) |     120 |          0 |
| DOOM Kitty | worker  | 74 (49–94) |           13 (9–25) |         2% (1–2) |     120 |          0 |
|            | page    | 62 (38–83) |       136 (109–162) |      14% (10–16) |     120 |          0 |

Keystroke echo, median of per-session p50s: **worker 0.95 ms** (0.90–1.30), **page 1.15 ms** (1.00–2.15). The p90s were 1.40 (1.10–2.50) and 1.70 (1.20–10.10).

- **Main thread:** on text, the main thread does about a third of the work it did before. With Kitty images it does about a tenth. The worker variant still uses 5–6% of the main thread on text, but script time is only 3–6 ms per workload. The remainder is probably `cursor` replies restyling the hidden input element on every frame, plus `stats`. That has not been profiled.
- **Throughput:** the two variants are within noise of each other. On this heavily loaded machine both ran well below the ~100–130 MB/s that PR #57 measured at lower load. The PTY and `serve` set the throughput ceiling, not the page, so the worker socket was not expected to raise it. One page run had a 6 MB/s logs outlier, under a load of 18.
- **Frames:** at these rates, both variants held the page at 120 rAF/s with no long tasks. The page path was busy 18% of the time, which was not enough to drop frames. The main-thread headroom matters when the page has its own work: other panes, application UI, or a slower device. This benchmark does not show that directly.
- **Echo:** the worker variant is about 0.2 ms faster at the median. That fits with one fewer hop: replies and keystrokes go worker → socket instead of worker → page → socket. The difference is small against the run-to-run spread.

## Limits

- Shared, heavily loaded machine. The serialized judge run should repeat this.
- Task time is Chrome's total for the page's main thread. It includes this harness's own rAF loop and observer, which both variants pay equally.
- The tests did not measure presentation to the physical display, or effects on other tabs.
- The `events` fallback (no `WebSocketStream`) was not benchmarked. It is covered by `test:worker-socket` for correctness only.

## Reproduce

```sh
npm run build:sdk
FILES=logs.ansi,ascii.txt,doomtext30.ansi,kitty60.ansi ROUNDS=6 PORT=6222 \
  OUT=ab.json node scripts/ghostty-native/serve-ab.mjs
```
