# Keystroke-to-pixel latency (native profile)

Provisional results from a shared machine: Apple M5 Max (18 logical CPUs),
macOS 27.2, Chrome 155, a headed window on the built-in display (120 Hz,
frame interval about 8.3 ms). Other agents ran builds and benchmarks at the
same time; 1-minute load average was 8.9 to 18.7 during the main run. Treat
these numbers as A/B evidence from one session, not as absolute latency. A
central serialized run is still needed.

## Method

`npm run benchmark:input-latency` ([script](../../../scripts/input-latency-benchmark.mjs))
starts `wraithterm serve` with `stty raw -echo; exec cat` in the PTY, so a
process echoes every typed byte back over a loopback WebSocket, as a shell's
line editor does. Playwright presses one lowercase letter at a time, waits for
its frame, then waits a random 10 to 40 ms so keystrokes land at random
phases of the display's refresh. The page and engine worker record each stage
on one clock (`performance.timeOrigin + performance.now()`):

| Stage    | Where it is recorded                                                       |
| -------- | -------------------------------------------------------------------------- |
| keydown  | `KeyboardEvent.timeStamp` (capture listener on the page)                   |
| key      | key command handled in the engine worker                                   |
| sent     | encoded bytes handed to `WebSocket.send`                                   |
| echo     | echo message received on the page                                          |
| parsed   | echo parsed by libghostty-vt in the worker                                 |
| submit   | `queue.submit` for the frame containing the echo returned                  |
| gpu      | `GPUQueue.onSubmittedWorkDone` for that frame                              |
| received | the canvas CompositorFrame reached Chrome's display compositor (viz trace) |
| swap     | the display frame drawing it was swapped (`STEP_SWAP_BUFFERS_ACK`)         |
| vsync    | the next vsync callback after that swap (`OnVSyncPresentation`)            |

Two conditions: idle, and during background output (a second process on the
same PTY writes about 2,000 lines/s of 100 uppercase bytes; lowercase bytes
identify echoes). Each round runs both variants in alternating order (A/B,
B/A) for both conditions in one browser session. A 32 MiB flood per variant
and round, timed from its first WebSocket message to its end marker being
parsed, guards throughput.

### What is and is not observable

- A WebGPU canvas has no presentation feedback: no
  `requestVideoFrameCallback`, no presentation timestamps on
  `GPUCanvasContext`. The worker's next `requestAnimationFrame` after submit
  (`frame` in the raw data) is a weak proxy and misleads here: it moves a
  full frame earlier when a frame is rendered outside an animation frame,
  whether or not the display does.
- The Chrome trace (`viz`, `gpu` categories) shows when viz received the
  canvas frame, drew it and swapped. It is mapped to page time through a
  `performance.mark` in the same trace. `vsync` is the next vsync callback
  after the swap. Chrome's CVDisplayLink reports about 11.6 ms from that
  callback's timebase to display output (`vsyncToDisplayUs`). That offset is
  the same for both variants and is not added. Physical scanout and panel
  response are not measured.
- Main-thread and worker timers are coarsened to 0.1 ms, so stage deltas
  across threads, such as `keydown->key`, are approximate.
- Tracing has some overhead. An untraced run ([ab-untraced.json](ab-untraced.json))
  shows the same submit-side difference.

## Results

Main run: [ab.json](ab.json), 4 rounds of 100 keystrokes per variant and
condition (400 each). Built at `d255384` with immediate frames switched on by
default; both variants run the same code, switched at runtime.

Keydown to stage, ms, p50 / p90 / p99:

| Condition | Variant          | submit           | swap                 | vsync                 |
| --------- | ---------------- | ---------------- | -------------------- | --------------------- |
| idle      | frame (baseline) | 5.3 / 8.8 / 10.1 | 6.69 / 10.23 / 11.87 | 13.37 / 16.72 / 18.08 |
| idle      | immediate        | 0.7 / 1.1 / 1.7  | 1.76 / 2.98 / 8.18   | 7.86 / 13.48 / 16.71  |
| output    | frame (baseline) | 5.1 / 8.6 / 9.9  | 6.38 / 9.94 / 17.21  | 13.18 / 16.87 / 25.14 |
| output    | immediate        | 5.3 / 8.3 / 9.8  | 6.62 / 10.04 / 15.50 | 13.39 / 16.61 / 22.49 |

Per-block p50, keydown to vsync: idle frame 13.49, 13.28, 13.95, 13.16; idle
immediate 8.18, 7.86, 7.46, 7.65; output frame 13.17, 13.05, 13.46, 13.22;
output immediate 13.87, 13.30, 13.43, 13.25.

Idle typing reaches the swap 4.9 ms sooner at p50 and the next vsync 5.5 ms
sooner (p90 3.2 ms sooner). With background output the two variants are
within noise of each other, as designed: frames there stay on animation
frames.

Throughput guard, 32 MiB flood through serve, MB/s: frame 34.2, 50.1, 39.2,
43.8 (median 43.8); immediate 39.2, 43.1, 42.7, 35.3 (median 42.7). The ranges
overlap; no regression is visible at this noise level. Serve's main-thread
socket path caps these runs, not the renderer.

### Where the idle time goes (immediate, p50 / p90)

keydown to key command in worker 0.2 / 0.3; key to `WebSocket.send` 0.1 /
0.1; send to echo received 0.3 / 0.6 (server, PTY and `cat`); echo to parsed
under 0.1; parsed to submit 0.1 / 0.2; submit to viz receiving the frame 0.15
/ 0.27; viz receive to swap 0.8 / 1.7; swap to next vsync 5.6 / 11.1.
`onSubmittedWorkDone` resolves 1.2 / 2.1 ms after submit. Most of the
remaining time is waiting for the display's refresh after the swap, which a
page cannot shorten.

## What shipped

A write to a terminal that has drawn no frame for two frame intervals (frame
interval estimated from consecutive animation frames) renders at once in the
worker instead of waiting for the next `requestAnimationFrame`. The trace
shows why this helps: when no BeginFrame is pending, viz draws and swaps a
canvas frame that arrives between vsyncs straight away, about 0.8 ms later,
instead of after the next vsync. Busier output keeps animation-frame pacing,
so a flood still renders at most about one frame per refresh.

## What did not help

- **One idle interval instead of two** ([idle-threshold.json](idle-threshold.json),
  variant `immediate` there): the same idle gain, but with background output
  (writes every 10 ms, longer than the 8.3 ms interval) off-phase frames mixed
  with animation frames and pushed p90 keydown-to-swap from 9.8 to 14.1 ms and
  keydown-to-vsync p90 from 17.0 to 20.7 ms. Two intervals (`idle2`) and three
  (`idle3`) did not regress output. Two was kept so 30 Hz key repeat on a
  60 Hz display still renders immediately.
- **Rendering every keystroke's echo immediately, even during output**
  ([input-priority.json](input-priority.json), variant `input`): the echo was
  submitted 0.7 ms after keydown at p50 instead of 5.5 ms, but swap and vsync
  were not earlier (p50 7.1 vs 6.8 ms to swap). Viz already had a frame from
  that refresh interval, so the extra frame waited for the next one. Not
  shipped. These two exploratory runs used uncommitted code at load averages
  up to 16; their flood numbers from the last round collapsed under load.
- **A low-latency canvas**: Chrome's `desynchronized` context attribute
  applies to 2D and WebGL contexts. `getContext('webgpu')` takes no context
  attributes, and `GPUCanvasConfiguration` has no latency or present-mode
  option (device, format, usage, view formats, color space, tone mapping and
  alpha mode only). The native canvas is already configured opaque. No WebGPU low-latency
  path exists to enable.
- **Main-thread hops**: keydown to `WebSocket.send` is 0.3 ms and echo to
  parsed under 0.1 ms on an idle main thread, so moving the socket into the
  worker (#58) cannot buy much idle latency. It matters when the page's main
  thread is busy, which this harness does not load.

## Remaining ideas

- Measure on a 60 Hz external display, where the frame wait is twice as long.
- Measure with a busy main thread, with and without the worker-owned socket
  from #58.
- Physical light-out latency needs a camera or photodiode; nothing in the
  browser reports it.

## Reproduce

```sh
npm ci && npm run build:sdk
npm run benchmark:input-latency            # 3 rounds x 100 keys, both conditions
WRAITH_ROUNDS=4 WRAITH_REPORT=docs/benchmarks/input-latency/ab.json npm run benchmark:input-latency
WRAITH_TRACE=0 WRAITH_FLOOD_MB=0 npm run benchmark:input-latency   # without the Chrome trace
```

The serve port defaults to 6224 (`WRAITH_SERVE_PORT`).
